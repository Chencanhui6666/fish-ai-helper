# 个人 Agent Harness 产品方案与学习路线

日期：2026 年 10 月 28 日。面向有 React 经验、开始学习 Python 后端的个人开发者。

目标是亲手实现一个能持续处理任务、调用工具、保存状态、接受人工干预和定位失败的 Agent 工作台。第一个业务场景沿用钓鱼助手，最终通过第二个场景验证运行框架可以复用。本文是待实现的产品与任务规格，不代表功能已经开发完成。

## 1 产品定义

产品暂名 Fish Agent Workbench。用户在工作台提出出钓需求，助手补齐条件、查询信息、检索个人资料并生成出钓计划；用户确认后，系统保存一份可以重新打开的计划。开发者能看到实际执行步骤、工具输入输出、错误和关联 Trace。

在这个项目里，harness 指围绕模型执行循环的一组可复用能力：上下文组装、工具注册、运行状态、记忆和持久化、执行边界、人工确认、产物管理、追踪和回归评测。LangChain 提供模型、消息、工具和预构建 Agent；LangGraph 承担自定义状态与流程编排；FastAPI 提供应用服务；React 展示运行状态和用户交互。不要同时维护两套功能相同的 Agent 循环。

### 最终演示脚本

1. 新建“周末出钓”会话，输入“周六想钓鲫鱼，帮我做个计划”。
2. 助手先询问地点、具体日期、作钓时段与装备。用户补充后，同一会话能记住这些条件。“周六”在执行前解析为明确日期并让用户确认。
3. 运行区展示“整理条件 → 查询天气 → 检索笔记 → 生成方案”。天气必须来自已配置的真实数据源；测试数据明确标记为测试，接口不可用时说明缺失，不伪造实时结果。
4. 用户打开查询步骤，可查看地点、日期、返回摘要与来源。展示执行事件和简短依据，不要求模型暴露隐藏思维过程。
5. 中间显示结构化计划预览。保存前弹出确认卡，允许确认、拒绝或修改。拒绝后不执行保存。
6. 确认保存后，右侧出现计划成果，包含时间、地点、目标鱼、装备、操作建议、依据和待确认项。支持重新打开与下载 Markdown。
7. 刷新页面能恢复历史；服务在等待确认时重启，仍能继续确认。工具超时有明确失败状态，并可对只读步骤重试。
8. 在同一运行框架中切换到“资料问答助手”，替换提示、工具和输出结构，复用会话、事件、持久化、审批和观测能力。

### 范围

V1 是本地单用户工作台，支持文字任务、持久会话、工具、显式流程、人工确认、成果、停止与恢复、上下文控制、追踪和基本评测。知识检索是 V1 的业务能力。图片识别作为 V1.1 的独立学习分支，因为当前模型的图片输入能力需另行验证。

账号体系、公共多用户服务、任意代码执行、工作流拖拽编辑器、插件市场和多 Agent 协作放在后续。它们不是当前学习闭环的前置条件。部署阶段先提供绑定本机的可复现运行方式，公开访问前另加认证、会话隔离和资源限制。

## 3 UI 与交互规格

### 桌面工作台

采用浅色中性底、青绿色主操作、清楚的文字状态，延续现有水域与钓鱼品牌。深色模式后置。桌面参考宽度 1440px：左侧会话栏约 240px，中间对话区弹性伸展，右侧详情约 360px。小于 1100px 时右侧详情改抽屉；小于 768px 时会话栏也改抽屉。320px 宽度可发送消息、处理确认、查看成果，无横向溢出。

| 区域 | 内容 | 关键交互 |
| --- | --- | --- |
| 左侧 | 新任务、会话列表、资料库、设置 | 切换后恢复消息、状态和待确认项；有活动运行时不丢失后台任务 |
| 顶栏 | 会话名称、场景、连接状态 | 场景在新任务时选择；已有会话固定场景，避免状态不兼容 |
| 中间 | 用户消息、助手回复、真实步骤、确认卡、输入框 | 流式回复、停止、错误后重试；滚动阅读旧消息时不强制拉到底部 |
| 右侧成果 | 出钓计划、版本、来源、下载 | 点击成果重新打开；修改时创建新版本，保留旧版本 |
| 右侧运行详情 | 步骤时间、工具参数/结果、错误、token、Trace 链接 | 默认折叠原始数据；敏感信息不出现在详情中；缺失指标显示“未提供” |
| 资料库 | Markdown/txt 列表、索引状态、删除 | 显示处理中、可检索、失败；删除后不再出现在后续检索结果中 |
| 设置 | 模型名称、能力、Tracing 目标、运行限制 | 密钥从后端环境读取；浏览器仅展示是否已配置 |

输入框首版支持文字，图片入口在后端支持前明确禁用并说明。普通聊天显示简单状态，复杂任务才展示步骤。开发调试详情默认收起，避免普通使用流程被技术信息占满。

### 必须设计的状态

空会话有示例任务；连接中/断开提供重连；正在执行可以停止；等待补充条件显示具体问题；等待确认显示动作和参数；工具失败显示原因和重试入口；用户取消显示保留的内容；完成显示成果；刷新恢复显示服务端真实状态。不能用一套“AI 正在思考”覆盖所有状态。

“停止”取消当前运行，不删除消息，不等同关闭 WebSocket。浏览器断线默认让服务端任务继续；重新连接后查询/补读状态。“取消”也不能保证撤销已发生的外部写入，需要清楚显示动作是否已执行。

## 4 技术与数据边界

### 分阶段架构

先用现有 create_agent 跑通异步消息、工具与记忆；需要业务条件分支时，用 StateGraph 显式实现“补条件 → 查信息 → 生成方案 → 等待保存确认 → 保存”。把模型和工具放在节点里。复杂工具循环可复用 create_agent 子图，已有流程不再另写同功能循环。

直接依赖 langgraph 后应在 pyproject.toml 声明，不能只依靠 LangChain 的传递依赖。保持当前 uv.lock，在开始每个新框架功能前核对实际安装版本；不把教程中的 API 名称当作当前环境的事实。

| 部分 | 首版选择 | 为什么这样安排 |
| --- | --- | --- |
| 服务 | FastAPI、Pydantic、asyncio | 从类型校验、异步和依赖注入学起 |
| 模型/工具 | LangChain | 保留已有模型适配层，支持可控假模型做测试 |
| 编排 | LangGraph | 学状态、节点、条件边、checkpoint、interrupt/resume |
| 存储 | SQLite；原型先内存 checkpointer，随后持久 SQLite checkpointer | 先掌握事务、索引、重启恢复，再考虑 PostgreSQL |
| 事件 | 保留 WebSocket；HTTP 管理会话/运行/成果 | 复用现有前端，业务命令和事件模型不绑定传输实现 |
| 知识检索 | 少量 Markdown/txt，先可验证的检索再接 embedding/向量索引 | 先理解文档、chunk、召回和引用，再引入额外基础设施 |
| 观测 | 应用 run 记录 + LangSmith | 应用负责用户能看到的状态，LangSmith负责开发追踪 |
| 验证 | pytest、前端 build、少量关键浏览器流程 | 重点验证状态、重试、恢复和协议，不为简单样式堆测试 |

### 标识与存储

conversation_id 是前端业务会话；graph thread_id 稳定映射到同一业务会话；run_id 是一次提交产生的执行；message_id 是消息；tool_call_id 是模型提出的工具调用；approval_id 是一次确认；artifact_id 是成果；event_id/seq 用来补读和去重。不要把 WebSocket 连接当作会话标识。

应用 SQLite 保存 conversations、runs、messages、events、approvals、artifacts、documents，以及有需要时的 tool_executions。Graph checkpointer 保存图的运行状态与消息 reducer；应用消息表是界面查询投影，不能与图状态各自任意修改。写明各字段的唯一约束、更新时间和数据来源。

同一会话 V1 只允许一个活动 run，包括等待审批；另一提交明确返回冲突。同一消息重发通过 client_request_id 幂等；工具写入通过 tool_execution_key 幂等。审批需匹配 run、approval、checkpoint/版本和当前等待状态；重复确认不能保存两次，过期确认返回冲突。

### 协议和运行状态

运行状态：queued、running、waiting_input、waiting_approval、succeeded、failed、cancelled。终态不可回到 running；重试创建关联的新 run。审批恢复可沿用同一业务 run，但关联新的执行片段与 Trace。工具步骤另有 pending、running、succeeded、failed、skipped。

事件统一有 schema_version、event_id、seq、conversation_id、run_id、type、timestamp、payload。事件类型至少覆盖 run.started、message.delta、message.completed、step.started、tool.started、tool.completed、approval.required、artifact.created、run.completed、run.failed、run.cancelled。已持久化事件按 run 内 seq 递增；前端按事件 ID 去重，恢复时先取快照再补读事件。写出快照与事件游标如何对齐，避免恢复时重复追加文本。

建议增量补充的 API：POST/GET /api/conversations；GET /api/conversations/{id}；POST /api/conversations/{id}/runs；GET /api/runs/{id}；POST /api/runs/{id}/cancel；POST /api/runs/{id}/resume；GET /api/runs/{id}/events?after_seq=；GET /api/artifacts/{id}。WebSocket 保留 /api/ws/chat，逐步改为按 run 订阅。资料和图片接口在对应任务再增加。路径是设计目标，不代表已有接口。

副作用包括保存计划。把 interrupt 放在副作用之前；恢复时节点可能重新执行，不能把已执行副作用放在 interrupt 前并期待它只执行一次。恢复后在事务里检查唯一执行键，再保存成果。跨进程恢复允许显示“上次运行中断”，按 checkpoint 恢复，不能让数据库里的 running 永远悬挂。

## 6 学习与协作方式

按每次 60～120 分钟、每周 4～6 次估算，主线约 8～12 周；这是学习排期假设，不是工期承诺。M0/M1 约 1～2 周，M2/M3 约 2～3 周，M4/M5 约 2～3 周，M6/M7 约 3～4 周。记录真实耗时后调整，不通过跳过恢复/验收来赶时间。

每次只取一张卡：先复述期望行为 → 学当前任务需要的一个 Python/框架概念 → 自己写最小实现 → 用明确样例验证 → 解释数据和控制流 → 提交。遇到问题时要求助手给提示、定位和审查，避免一次生成整套实现。前端擅长部分尽量复用，主要精力投入异步、数据库、状态编排和故障恢复。

每张卡完成后回答三个问题：数据放在哪里？失败或重启后会发生什么？为什么选当前实现？能说清楚并独立改动，才算完成学习目标；复制出能跑的代码不单独算学会。

## 7 完成标准

- 用户体验：任务从输入到可保存成果完整闭环；支持补条件、查看步骤、确认/拒绝、取消、历史与恢复；移动布局能处理主要操作。
- 后端：输入与输出有 schema；异步请求不相互阻塞；会话隔离；持久化与事件补读一致；人工确认、重试、恢复不重复副作用。
- Harness：上下文、工具、运行边界、状态、记忆、人工确认、成果、观测和评测可以跨两个业务场景复用。
- 验证：关键流程有自动化或可重复验收证据，失败时能定位到具体步骤和 Trace；20 条固定评测有结果报告。
- 全栈交付：可以从空环境启动、配置、运行、持久化、备份并定位问题；公开部署前另行完成认证与隔离。
- 个人能力：你能自己新增工具、加条件分支、修改数据模型并解释异步、事务、checkpoint 与 API 的关系。
